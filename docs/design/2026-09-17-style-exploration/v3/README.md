# A+B 融合版：门店工作台

日期：2026-09-17。状态：本地可点击原型，待用户评审；未改造生产业务前端，未接入后端或部署。

## 用户反馈与本轮方向

- 用户希望保留 B 的美感，并吸收 A 中顺手的订单处理功能。
- 用户明确指出 B 的手机 / App 效果图操作不顺：大图占据首屏、横向找设备、任务和处理入口过于靠后。
- 本轮以 B 的奶油白、森林绿、衬线标题、细分隔线和设备摄影为视觉基础，加入 A 的任务筛选、选单即处理、进度、检查清单和尾款信息。
- 原 A / B 保留在 `../v2/`；当前融合方向位于本目录，不把它记成已最终批准的设计。

## 界面分工

| 场景 | 融合后的处理 |
| --- | --- |
| 桌面首页 | 顶部六项导航与统计，左侧待办检索，右侧设备图和订单处理并排；1366×768 首屏可见主按钮。 |
| 设备看板 | 保留照片选单方式；选中设备进入同一份订单，不另建一套订单状态。 |
| 手机首页 | 顶部开单、统计筛选、搜索、竖向待办；移除重复大日期标题和横向大图主入口。测试视口首屏可见 3–5 条完整待办，390×844 可见 4 条。 |
| 手机详情 | 独立详情页、紧凑照片摘要、进度及检查项，底部固定尾款与当前动作；照片可点开。 |
| 手机返回 | 页面返回按钮及浏览器返回均回到原来的列表 / 看板；恢复背景交互。 |

按钮随事项变化：交付单办理交付，缺件单核对到货 / 查看缺件，维修单检测 / 确认方案，回收单先验机。不能给所有设备显示同一张交付检查表。

## 已实现的交互

- 七条虚构订单，交付 2、缺货 2、维修 2、回收 1；应收 ¥12,800 来自三条销售订单，统计与列表一致。
- 按事项或应收筛选；按客户、单号、设备、示例 SN 检索，支持 Ctrl/Cmd+K；无结果时清空旧详情。
- 按订单隔离、切换后保留的本次会话检查状态；刷新恢复示例初值，不写浏览器持久存储。
- 设备看板与待办共用数据；订单详情展示各自金额、进度、缺件或维修事实。
- 配置清单、客户资料、照片、处理记录、下一步核对对话框；原生 dialog 支持焦点限制、Escape 关闭。
- 交付核对显示未完成检查和待收尾款，未实现收款或交付提交，不伪造完成状态。
- 回收估价保留“尚未确认收购”的状态，客户送修 / 暂存设备不表示为可卖库存。

开单、库存等其他模块导航仍为明确的操作预览提示。本轮没有完整重做 ERP，也没有实现扫码相机、拍照上传、实际微信小程序或原生 App。

## 验证

```powershell
node --check docs/design/2026-09-17-style-exploration/v3/workspace.js
node docs/design/2026-09-17-style-exploration/v3/verify.cjs
```

使用项目已有 Puppeteer 和本机 Microsoft Edge。覆盖 1366、1440、1024、768、320、375、390、430 宽度：页面与手机详情无横向溢出，示例图片正常；1366×768 主动作可见；四种手机宽度的检查清单和固定主动作同时可见。

同时检查 21 项交互，包括按单金额与检查状态隔离、筛选后的选单、无结果、示例 SN 搜索、交付未完成事项、图库进入、手机返回、弹窗关闭、按需查看照片、窗口尺寸切换。结果与截图只证明本地网页原型，不证明后端业务、真实数据、微信胶囊、安全区、软键盘或原生 App 已验收。
