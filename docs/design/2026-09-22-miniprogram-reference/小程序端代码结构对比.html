一条硬事实

「原生 TypeScript + 完整业务闭环 + 高星」的小程序项目，开源里不存在。
按 TypeScript 筛，最高才 48★（2021 年的模板）；高星的（21.8k / 2.6k / 859）全是 JS。原因：高星项目基本成形于 2017–2019 年 JS 时代，TS 化是近几年的事，而成熟的企业级项目通常不开源。

⇒ 所以能选的路只有三条，见最后一节。

你真正缺的三样

  1. components/ —— 组件化目录（最缺）。你现在是页面直接写 WXML，没有任何可复用组件。顾客端页面一多，重复结构会迅速失控。可直接照抄的三个最通用：custom-image（图片占位/失败兜底）、custom-nav-bar（自定义导航，绕开原生导航栏的限制）、custom-broken-network（断网态）。
    → 抄 zhihuifanqiechaodan/miniprogram-template，它这四个通用组件就是为这个场景做的。
  2. store/ —— 状态管理。你的 features/session.ts 相当于手写的轻量版，但没有统一 store。跨页共享「当前报价单 / 登录态 / 购物车」时会散。Weapp-Starter 用 store/ 解决，模式可直接借鉴。
  3. typings/ —— 类型定义分层。你现在类型只有 contracts/generated（协议层）。缺小程序自身的类型分层（API 响应类型 / 页面数据类型），Weapp-Starter 与 zhihuifanqiechaodan 都有 typings/api-types 这样的结构。
反过来，有一样你做得比它们都好：scripts/check-pages.mjs + check-classes.mjs + 8 个单测 + 契约生成物同步。TDesign 零售有 eslint/husky 但没有这类业务自检。这部分不要丢。

三条路，你选一条

  1. A · 不换底座，只补结构（推荐）。在现有项目上补 components/、store/、typings/ 三层。代价最小，且不破坏已通过的契约同步与自检链路。你现在的结构已经是原生 TS 里靠前的，推倒重来是净亏。
  2. B · 换 TDesign 零售模板作底座。结构分层最规范（services/ 按域拆 + components/ 10 个业务组件），但它是 JS，TS 化要补全量类型；且它的业务（零售电商）与顾客端（报价单）差得远，要删改一半。只在"你想顺带把代码规范统一"时才值。
  3. C · 换 wechat-app-mall 作底座。功能最全（50+ 页面、支付/物流/售后都有），但 pages/ 扁平堆 50+ 个，结构乱、代码老、无 TS。改造量大于自建，不建议。
共同前提：无论走哪条，视觉都不要从这些项目里抄——你说得对，它们都丑。它们能提供的只有目录分层、组件划分、工程配置这三样。
