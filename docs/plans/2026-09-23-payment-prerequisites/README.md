## 2. 现有可复用底座（支付的「记账半场」已经建好）

这是本轮盘点最有价值的结论：**后端账本与幂等已相当完整，在线支付能直接接上去，不用从零做。**

| 能力 | 位置 | 可直接复用之处 |
|---|---|---|
| 统一资金流水 `cash_entries` | `backend/migrations/0013_sales_core.sql:184-216` | 方向 / 金额 / 方式 / 往来主体 / 来源单据 / 冲销引用齐全；`purpose = 'sale_order'` 时 DB 强制 `sale_order_id` 非空（:211） |
| 强幂等 | `0006_consistency_core.sql:20-36` + `domains/operations.ts` | `UNIQUE (store_id, request_id)` + `payloadHash`；同 ID 同载荷返回原结果 |
| 结果未知的查询机制 | `contracts/v1/errors.json:15-20`、`operations.ts:501-506` | **超时 ≠ 失败**；用 `GET /operations/:requestId` 先查再决定是否重发 |
| 余额恒等式 | `contracts/v1/money-rules.json`、`backend/src/domains/sale.ts:1284` | 到账只影响现金净收，余额与方向自动派生，无需新公式 |
| 部分收款（内生） | `sale.ts:1297-1307`、`sale.ts:171-173` | 收多少都行，上限 `max(余额, 0)`；**定金与全款是同一机制**，不需要两个实现 |
| 定金门槛已实现 | `sale.ts:179-190`（`requiredDepositCents`）、`sale.ts:980-1001` | 门槛 = `ceil(总额 × depositPercent / 100)`；可用 `terms_snapshot.depositPercent` 覆盖；快照损坏时按门店参数走（不会把「读不出来」升级成「不用付款」） |
| 「付定金才预留」闸门 | `sale.ts:992-1001` | 注释原文：「未付款不预留：已核实收款 + 折抵 必须达到定金门槛」——**业务规则已有代码支撑** |
| 纠错路径 | `finance.ts:79/199`、`CashEntry.reversalOf` | 不删不改原流水，新增等额反向记录 |
| 权限范式 | `access.ts:102-109`、`actions.json:242-248` | 收款类动作走 `explicit` / `owner_only` 闸门，受 `noWidening` 保护 |

**可复用的踩坑经验**：`sale.ts:196-204` 记录了订单号生成的真实缺陷——原来取 requestId 前 8 位，导致「公共前缀 + 序号」的 requestId 必然撞号且报错指向完全错误的方向。修法是**对整个 requestId 求稳定哈希**。⇒ **支付单的商户单号必须照此实现**，不得取前缀、不得递增计数。

| G5 | **支付动作编号与路径** | `ActionCode`（`enums.json:228-239`）无支付相关编号；`pending` 只登记 B39 / B40 |

### 3.1 一个必须提前知道的工程风险

`cash_entries.method` 与 `purpose` 是 **`CHECK` 约束硬编码的枚举**：

```sql
method  TEXT NOT NULL CHECK (method  IN ('cash','wechat','alipay','bank','other')),   -- :189
purpose TEXT NOT NULL CHECK (purpose IN ('sale_order','service_order','purchase','recovery')),  -- :195
```

⇒ 若在线支付需要新的 `method` 值（如区分平台到账）或新 `purpose`，**SQLite 改不了 CHECK，必须重建表**（照 `0017_sale_refund_credit.sql` 建 `sale_orders__v17` 的路子）。

**建议优先选择「不改这两列」的方案**：让支付单对象自己承载「平台到账」语义，到账后仍写 `method = 'wechat'` 的普通流水，靠 `PaymentIntent.cashEntryId` 反向溯源。这样能**避免一次伤筋动骨的表重建**。是否采用，见 §6 待拍板。

## 4. 契约设计草案（建议，未冻结）

### 4.1 五条核心原则（沿用现有契约，不新造世界观）

1. **服务端重算为准**：客户端不得传最终金额（`conventions.json:125`）。
2. **支付单是辅助对象**：不改 `SaleTradeState`；销售单支付状态继续「由流水与余额派生」（`objects.json:190`）。
3. **到账就是一条流水**：不发明第二套账本。支付单成功后派生一条 `direction = 'in'` 的 `cash_entry`。
4. **未知不是失败**：网络超时 / 回调未达一律进「结果未知」，保留查询入口。
5. **库存冲突不吞钱**：到账成功但库存冲突 → 保留真实收款 + 进门店待处理（[产品与架构](../2026-09-22-customer-miniprogram-reset/01-product-and-architecture.md) §6 已定）。

### 4.2 支付单对象草案

建议命名 `PaymentIntent`（避免与 `CashEntry` 混淆）。字段草案：

| 字段 | 类型 | 说明 |
|---|---|---|
| `saleOrderId` | id | **挂载点**，必须指向已成立销售单 |
| `quoteVersionId` | id, nullable | 冻结「这笔钱对应哪个报价版本」 |
| `purpose` | enum | 草案 `deposit` / `balance` / `full`；D06已定首版为预付款，若保留deposit技术名，须显式表达款项性质，顾客不可显示法律定金承诺 |
| `amountCents` | cents | 服务端算出的应付，**不接受客户端传值** |
| `status` | enum | 见 4.3 |
| `merchantOrderNo` | string | 本地商户单号：**幂等生成、与支付单一一对应**（照 `sale.ts:196-204` 的稳定哈希做法） |
| `platformTradeNo` | string, nullable | 平台单号，回调后回填 |
| `expiresAt` | timestamp | 支付单有效期 |
| `paidAt` | timestamp, nullable | **服务端确认到账**的时间（不是客户端回调时间） |
| `cashEntryId` | id, nullable | 到账后派生的流水 ID，用于溯源与防重复入账 |
| `failReason` | string, nullable | 失败 / 关闭原因 |

### 4.3 支付单状态机草案

```text
created ──下单成功──▶ prepay_created ──平台确认到账──▶ paid
   │                        │
   │                        ├── 用户取消 / 超时 ──▶ closed
   │                        ├── 明确失败 ────────▶ failed
   │                        └── 结果未知 ──▶ outcome_unknown ──查询──▶ paid / closed
   └── 下单失败 ──▶ failed
```

要点：

- `paid` **只能由服务端可信事实进入**（验签通过的回调，或主动查单确认）。**客户端 `success` 回调不能改状态**——这是 MP58 / MP59 放行条件的原文。
- `outcome_unknown` 是**可停留状态**，必须保留查询入口，不能自动判失败。
- 一张销售单可有多张 `paid` 支付单（定金 + 尾款），但同一 `merchantOrderNo` **只能入账一次**。

### 4.4 应付口径（定金 / 全款）

| 时点 | 应付金额来源 | 现状 |
|---|---|---|
| 预付款 | `requiredDepositCents`（`sale.ts:179-190`） | D06已定统一15%；机制已有，新条款、款项性质和异常规则仍待收敛 |
| 尾款 / 全款 | `max(balanceCents, 0)`，即 `collectableCents` | 已可用 |
| 支付单有效期 | 独立于报价有效期 | 需定值（平台侧一般 2h 量级，以接入时官方为准） |

比例已冻结；余下要验证条款版本、预付款性质、混合折抵、改价/改址、晚到付款和退款并发。不能因已有15%计算就认为支付可用。

### 4.5 重复入账保护（三层）

| 层 | 机制 |
|---|---|
| 支付单层 | `merchantOrderNo` 唯一；同单号重复下单返回**原支付单**，不新建 |
| 回调层 | 去重键 = 平台单号 + 事件类型 + 本地支付单 ID；重复通知直接返回成功，**不重复入账** |
| 流水层 | 复用 `operations` 的 `UNIQUE (store_id, request_id)`；`cashEntryId` 已存在则不再写第二条 |

⇒ 任一层拦截都安全。三层同时存在，是因为**钱不能靠单点防重**。

### 4.6 回调 / 主动查询 / 对账

| 环节 | 要求 |
|---|---|
| 回调 | **验签 + 解密通过才算可信**；核对商户号 / AppID / 本地单号 / 金额 / 币种**全部一致**才入账 |
| 主动查询 | 结果未知时按本地单号查平台；查得已支付走**同一入账闸门** |
| 对账 | 与 ERP 的 `CashVerificationState` 衔接，但**语义分离**：平台到账 = 自动来源；人工登记仍为 `unverified` |
| 差错记录 | 金额不符 / 单号不存在 / 重复通知全部落 `operations` 与失败记录，**不静默丢弃** |

⚠️ 协议细节（接口路径、字段名、签名算法、证书轮换）**本文件不复刻**——按 MP58 卡要求「按当前支付官方协议」在实施时核实。

### 4.7 到账之后：与 ERP 动作的衔接

到账（`paid`）**不等于**自动锁库存。建议衔接顺序：

```text
平台确认到账
   → 写 cash_entry(direction = in) → 重算 balance
   → 达到定金门槛 → 触发预留（B05）/ 采购
   → 库存冲突 → 保留收款，进「待门店处理」，不退款、不回滚
```

MP57 已明确前置约束：**预支付不记到账、不预留、不触发采购**。⇒「到账 → 预留」的触发点属于 MP58 与衔接设计，**必须在 MP56 冻结**，不能各卡自行决定。
