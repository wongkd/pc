## 1. 检测状态流转

### 评审前现状与限制（基线 HEAD `9b9eae4`）

- `stock_items.availability` 是库存去向桶：`available`、`reserved`、`quarantine` 等。`quarantine` 还承载待检、故障、整备等不同原因，不能直接翻译成“待检测”。
- `stock_items.inspection_ref` 是 B19 检验审计引用。新建的期初实物可直接进入 `available` 且 `inspection_ref` 为空；已有引用也只证明发生过一次 B19 记录，不能说明当前仍待检、已通过或仍有故障。
- B19 只接受当前位于 `quarantine` 的实物，目标是 `available` 或 `retired`；结果 `pass/fail` 与去向目前分别传入，未强制配对。检测结果、发现和附件写入 `audit_logs.details`，没有独立的当前检测状态字段或可按状态汇总的读模型。
- 因此 U01 只统计真实库存桶；**检测状态数量是 U02 依赖，当前不提供或推算**。

评审时源码入口：[库存领域的期初与 B19](../../../backend/src/domains/inventory.ts)、[库存读写路由](../../../backend/src/routes/inventory-v2.ts)、[StockItem 字段](../../../contracts/v1.1/objects.json)、[库存桶与 B19 规则](../../../contracts/v1.1/enums.json)。当前决定与实现见本文件第 3 节及[验证回执](../../verification/2026-09-27-U02-inventory-semantics/README.md)。

### 方案比较

| 选项 | 设计 | 兼容与代价 |
|---|---|---|
| A · 独立状态投影 + 检测事件（推荐） | `StockItem.inspectionStatus` 取 `unrecorded / pending / passed / failed`；新增追加式检测记录，保存结果、发现、附件、操作者、时间、版本和 requestId。库存去向仍由 `availability` 表达。新来源明确写 `pending`；B19 记录事件并更新当前状态。 | 旧行迁移为 `unrecorded`，不按桶或旧 `inspection_ref` 回填；旧 B19 请求字段可保留，但要补结果与去向守卫。需契约、迁移、读写和状态筛选门禁。 |
| B · 只追加检测事件，读取时取最新事件 | 不增加 StockItem 当前状态列；由检测事件按时间 / 版本求最新结果。 | 历史完整、避免双写，但每次列表筛选需做最新事件读模型；查询、索引和事件缺失/并发语义更复杂。 |
| C · 维持现状并暂缓检测状态 | B19 仍只作 `quarantine` 出桶记录；暂不提供“待检测/已检测”筛选和统计。 | 没有迁移风险，但新建存量直接可售等旧路径缺口继续存在，U02 不关闭。 |

### 兼容、查询与验收影响

- **A**：v2 读响应新增可空/可枚举的 `inspectionStatus`，旧客户端忽略新增字段即可；历史行统一记为 `unrecorded`，不按旧桶或 `inspection_ref` 回填。按门店、状态、库存桶过滤与统计可直接使用当前状态列；事件表保留历史。验收需覆盖新旧记录、B19 结果与状态同事务更新、重复 requestId、版本冲突、完整筛选统计，以及失败件不能被标为可售。
- **B**：旧响应不变，但列表查询需要按实物取最新检测事件，按状态统计也须对全量实物解析最新事件；验收还要证明事件排序、并发写入和“无事件”读取稳定。若后续为性能增加投影，复杂度会接近 A。
- **C**：API / 查询 / 旧客户端均不变；验收明确不展示检测状态，只确认库存桶仍按原字段含义读取。新登记直接进入可售的现有风险也继续存在。

### 推荐的转换草案

若选择 A，推荐 `unrecorded → pending → passed / failed`；返修后由明确动作把 `failed → pending`，再做新一轮检测。`passed` 不自动等于可售：库存桶和其他上架条件仍单独守卫。首次版本不增加“免检测”状态；如确有不适用配件，再单独决定字段取值和证据规则。

B19 应只接受待检或返修后待复检实物；`pass` 只能记录通过，`fail` 只能记录未通过，未通过不得转 `available`。是否允许检测通过后继续隔离、是否允许直接退役，须与独立的整备/报损/退供动作分开裁定。每次转换沿用 expectedVersion、同 requestId 幂等和审计记录。

### 决策时待确认事项（已于第 3 节确认）

1. 检测模型选 **A（推荐）**、B，还是 C？
2. 若选 A，存量无可核实检测结论时接受显示 `unrecorded（历史未记录）`，并由后续实际检测更新吗？还是要先逐件复核后才启用新列表？
3. 对检测失败件，是否确认“留在待处理桶，先返修再复检”，不允许 B19 直接放回可售？

未获确认前，U01 不增加检测状态筛选或检测状态数量，也不将 `quarantine` 命名为“待检测”。

## 2. 同型号分批补录

### 现状与旧守卫

B13 期初登记会检查该商品是否已有门店自有实物或既往库存流水；已有事实时拒绝再次登记。两个守卫都排除本次 request 自己刚写的记录，以允许同一单内多行，但并未因此放开第二个独立批次。相同型号不能用另建同名商品绕过。

实现入口：[planOpening](../../../backend/src/domains/inventory.ts)、[B13 路由](../../../backend/src/routes/inventory-v2.ts)、[期初接口约定](../../../contracts/v2/inventory-opening.json)。

### 方案比较

| 选项 | 设计 | 兼容与代价 |
|---|---|---|
| A · 新增专门补录动作（推荐） | 保留 B13 的首批期初语义和两个旧守卫；新增明确的“已有库存补录”动作/端点，按现有 trackingMode 增加数量或建立逐件实物。使用稳定 `batchRef` 与行引用做批次级唯一约束。 | 新动作编号、权限、审计和契约需单独登记；行为边界清楚，旧客户端仍走旧守卫。是否复用期初表或另建批次表，需在实现设计中核定。 |
| B · B13 显式版本化扩展 | 旧请求省略新字段时仍严格执行原守卫；新客户端必须提供明确版本 / `mode=restock`、稳定 `batchRef` 和行引用，才允许新增批次。 | 单端点兼有首批与追加两种含义；要确保旧载荷永远不能隐式进入补录分支，并为批次身份增加可唯一约束的存储。 |
| C · 保持单批限制，先不支持 | B13 继续拒绝第二批；待盘点/纠错规则确定后再做。 | 不影响现有保护，但日常整理第二批时没有正式路径。 |

### 防重与身份规则

- 同 `productId` 不是重复：新批次可以是同型号的另一件实物；不得按型号名、商品 ID 或近似成本直接拒绝。
- 同 requestId + 同载荷重放应回读第一次结果，不增加余额/实物；同 requestId 改载荷应报幂等冲突。
- 同 `batchRef` 再提交（即使换了 requestId）必须命中批次唯一约束并返回已存在结果或明确冲突，不能再次增加库存。客户端须在首次发送前持久化并在超时重试时复用 `batchRef`、行引用和 requestId。
- 有厂家 SN 时用现有规范化唯一性守卫阻止登记同一序列号；无 SN 时自动内部编号只能标识本次新建记录，无法证明它不是已经登记过的同一件实物。此时展示近期相似登记供人工确认，不宣称算法已可靠识别；内部编号冲突仍必须拒绝。
- 客户所有物不能走“店里已有”补录；数量商品仍只记数量，不自动切换为逐件管理。

### 推荐与验收影响

推荐选 A：B13 继续只代表首次期初，第二批走专门动作。验收至少覆盖：相同商品不同 `batchRef` 可增加第二批；同批次重试不重复；新 requestId 复用已用 `batchRef` 不重复；同 SN 重复拒绝；无 SN 的相似件需要人工核对提示；跨店与权限拒绝；商品 trackingMode 不被修改；旧 B13 重放及旧守卫保持原样。

### 兼容、查询与验收影响

- **A**：新增动作与权限，不改变既有 B13 请求及读接口；补录成功后既有库存查询自然读取新增的数量余额或逐件行，批次审计查询可按 `batchRef` 回看本批结果。验收重点是新旧 B13 守卫不变、不同批次可追加、同批重放可回读、换 requestId 重复 batchRef 被拒绝或回读，以及跨店/权限/成本边界。
- **B**：需要版本化载荷、版本门禁和批次存储；旧客户端缺少版本字段时必须始终走原 B13 守卫。读模型同 A，但写入口同时承担首次期初和追加，验收必须覆盖旧载荷仍被旧守卫拦截，避免兼容分支误放开。
- **C**：接口、查询和旧守卫完全不变；验收只确认第二批仍被拒绝，日常补录能力继续未交付。

### 需要确认

1. 追加入口选 **A（专门补录动作，推荐）**、B（B13 显式版本化扩展），还是 C（暂缓）？
2. 若选 A 或 B，是否接受 `batchRef` 在首次发送前生成并持久化，重试始终复用；同型号但不同 `batchRef` 视为新批次？
3. 无 SN 的相似实物只做人工复核提示，是否接受“不保证自动判断同一件货”？

## 3. 已确认决定与本地实现

用户确认采用以下两项 A 方案，子规则一并确认：

1. **检测状态采用“当前状态字段 + 追加式检测事件”**。旧记录显示 `unrecorded（历史未记录）`，不按旧库存桶或 `inspection_ref` 回填。检测失败后须先完成返修登记（B48），再用新的 requestId 走 B19 复检；失败不能直接标为通过。新来源的逐件实物进隔离桶并标记 `pending`；数量管理型号没有逐件检测状态。
2. **同型号补录采用独立 B47**，保持 B13 原有首批期初守卫。首次提交前持久化并在重试时复用 `batchRef` 与明细 `lineRef`；同批换 requestId 不得再次增加库存。SN 重复会拒绝；无 SN 的相似件只提示人工复核，不承诺自动判重。

本地改动包括契约 v1.2、追加迁移 `0032_stock_inspection_and_backfills.sql`、B19/B48 检测流转、B47 补录命令、检测状态筛选 / 统计 / 明细事件读取，以及前端 API 类型和补录引用持久化。迁移尚未应用，生产未写入；U03 页面与 U04 来源关联仍未开始。实际门禁和未验证范围见[U02 验证回执](../../verification/2026-09-27-U02-inventory-semantics/README.md)。
