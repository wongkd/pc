## 执行顺序

1. 只检查配置中的目标/绑定，不输出密钥值。证明本地 D1、测试持久化目录、API base URL 均隔离；不能证明时停在静态检查，不运行可能访问远端的动作。
2. 重新运行契约校验、两端生成同步检查、客户端一致性。历史 23 项失败不是本轮结果；按失败分类，修当前实际问题。
3. 串行运行前端 test/build、后端 test/error-codes；记录现存失败与本卡新增失败，禁止吞掉失败断言。
4. 输出客户/角色模型提案：客户 ID、同名区分、联系方式访问权限、员工/顾客身份关联、门店归属、旧报价 ID 兼容。`customerId` 不等于已有 customers 表。
5. 输出内部订单/商品读模型与对外报价读模型字段白名单；金额单位、null 成本、版本号、requestId/operationId、错误语义统一。
6. 先形成可审查兼容与迁移设计，再由负责人安排实现及编号。真实支付/小程序凭证不属于本卡。

## 交给下游的接口契约

输出字段表、成功/失败 JSON 样本、角色矩阵、生成命令、兼容策略到本卡验证目录；路径和方法须据现有契约确认，不直接发明第二套 `/api`。
顾客输出排除成本、供应商、SN、内部备注及他人数据；员工成本权限独立。
所有写动作复用 operations 幂等边界，不用前端防抖代替服务端幂等。

## 验收与停止

契约检查全绿或明确列出阻塞；隔离证据可复核；同名客户/跨客户读取/成本无权/会话失效有负向样本。
需修改远端绑定、应用生产迁移、破坏历史 ID 或兼容资料时停止该动作，留下本地提案。
