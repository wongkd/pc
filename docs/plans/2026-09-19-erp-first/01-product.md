# 产品范围与业务闭环

日期：2026-09-19。状态：ERP 优先规划。入口：[规划总览](README.md)。

先读 [原始需求对照](00-requirements.md)。以下阶段是开发顺序，销售、维修、回收拆件、置换都在完整首版范围内。

## 1. 产品定位

让老板每天知道“哪张单卡在哪里、今天该处理什么、还差多少钱、配件在哪”，并在对应单据里办完事情。
默认单门店、少量人员；已有 store_id 隔离继续保留，多店调拨和总部管理延后。
电脑网页是内部 ERP；原生微信小程序是顾客的报价确认、下单、付款和查询入口。
ERP 的客户档案不能依赖顾客先有微信账号；将来绑定微信身份，不另造重复客户。

## 2. 角色与权限

以下为拟定默认角色，具体权限码在 E02 映射既有契约，不能据表直接放宽现有权限。

| 角色 | 高频事项 | 默认数据和动作边界 |
|---|---|---|
| 老板 | 报价、例外处理、采购、收支、利润 | 门店经营权限；退款、库存调整、角色管理留操作记录 |
| 店员 | 客户、开单、收款登记、交付 | 根据授权办理；进价、利润、退款审批分别授权 |
| 装机/维修人员 | 领件信息、装机、检测、维修记录 | 查看所需配置与设备；默认不返回成本及财务明细 |
| 顾客（后续） | 自己的报价、订单、付款和进度 | 服务端独立对外读模型，不返回成本、供应商、SN、内部备注或他人资料 |

一人经营可以兼任角色；不引入每一步都要两人审批的流程。库存、退款等关键动作仍须显示影响并留痕。

## 3. 模块与页面职责

| 导航域 | 主要页面 | 核心操作 | 优先级 |
|---|---|---|---|
| 工作台 | 今日待办、异常、近期交付 | 选单、处理卡点、回看操作结果 | B |
| 销售 | 报价列表/编辑/版本、订单列表/详情、配置模板 | 开单、比较版本、确认、收款、交付 | B |
| 库存 | 商品、逐件实物、数量库存、客户保管、流水、采购与供应商 | 找件、查占用、入库、分批到货、后续盘点调整 | B/C |
| 销售 → 客户 | 客户档案、设备、报价/订单/售后时间线 | 快捷建档、找历史配置、查质保依据 | B |
| 维修售后 | 接机、检测、方案确认、维修、返还 | 配件替换、保管、费用及原销售单关联 | C |
| 回收置换 | 估价、验机、收购、拆件、再销售 | 确认来源、成本分摊、退款/折抵关联 | C |
| 收支 | 收款、退款、采购付款、应收应付、日结 | 账单追溯、差异处理；后续经营统计 | B/C |
| 设置（底部） | 门店、成员权限、业务参数、打印模板 | 配置有效期/定金参数、权限和对外资料 | B |

侧栏保持工作台、销售、库存、维修售后、回收置换、收支六个业务入口。客户归销售且可从全局搜索直达；采购与供应商归库存。
SN 属于实物与设备详情，不独占顶层导航。装机在销售订单内处理，不重复建单。
尚未实施的 C 模块不在营业版显示空白入口，原型可以带明确演示标识展示全貌。
首版收支是经营台账，不承担完整会计总账、税务申报或电子发票系统职责。

## 4. 装机销售主流程

```mermaid
flowchart LR
  A[客户需求与预算] --> B[报价草稿]
  B --> C[发出版本]
  C --> D[客户确认配置与价格]
  C -->|提出修改| B
  D --> E[待收款订单]
  E --> F[核实定金或全款]
  F --> G{配件是否齐备}
  G -->|现货| H[预留库存]
  G -->|缺件| I[采购与到货验收]
  I --> H
  H --> J[装机与检测]
  J --> K[核实尾款与交付条件]
  K --> L[交付并正式扣库]
  L --> M[客户设备与售后档案]
```

报价可多次修改，但已发版本不覆盖；客户确认后的变更必须形成新版本并重新确认。
首阶段由店员记录线下/微信沟通确认的时间、来源和备注，标注“门店登记确认”；不能冒充小程序在线确认。
允许创建待收款订单以便跟进，但未付款不得预留实物、触发订单采购或进入实际装机。
收到定金即可进入备货；装机与全款的前后条件在实现卡映射已确认规则，交付默认要求结清。旧需求中的老板特批欠款交付作为受控例外保留：金额、到期日、原因、授权和应收待办缺一不可，不能标记已结清。

## 5. 状态不能混成一列

同一订单可以同时“已收定金、缺一件显卡、今日应交付”。页面同时展示这三个事实，不能用“进行中”覆盖。

| 维度 | 展示语义（待映射契约，非新枚举定义） | 改变它的真实动作 |
|---|---|---|
| 报价 | 草稿、已发出、已确认、已更新、过期、撤回 | 发出/新建版本/确认/续期/撤回 |
| 资金 | 待收、部分收款、已结清、退款处理中、部分/全部退款 | 收款核实、退款记录和冲正 |
| 履约 | 待备货、缺件、装机中、待检测、待交付、已交付 | 预留、到货、装机记录、检测、交付 |
| 异常 | 超期、金额待核实、库存争用、客户变更、待退款 | 处理具体异常，不靠任意改状态 |

状态由服务端根据业务事实计算；按钮是“登记到货”“完成检测”“办理交付”，不让店员用状态下拉框跳过业务条件。
库存预留到期后必须释放对应预留并生成异常待办；不能同时把已收定金订单静默取消。天数未定，不硬编码 7 天。
收款成功但预留失败时保留真实收款，转“已收款/缺件待处理”；提供采购、改配或退款路径，不能抹掉钱账。

## 6. 独立但可关联的业务

- **配件零售：** 商品/实物→客户或散客→价格→核实收款→交付扣库，省去装机检测步骤；有 SN/质保的商品建立设备关联。
- **维修售后：** 接机并登记附件/外观→检测→费用和方案确认→维修/换件→复测→结算返还；未同意付费方案不能默认开修。
- **回收：** 估价不入库存；确认收购与实际接收后记录所有权，验机合格才可用。用户已确定旧整机拆件入库、不整机转卖。拆出零件记录来源整机、检测、分摊成本、损耗、质保与去向，成本守恒。
- **置换：** 销售单与回收单分别存在，明确折抵关联；不通过随意改配件单价掩盖回收和资金。
- **客户保管：** 客供、送修、暂存设备登记归属与流转，不能计入可售库存或门店资产。
- **盘点：** 记录账面、实盘、差异与原因，授权后生成调整流水；禁止直接改库存数字。

### 须在界面上直接表达的门店规则

- **配送：** 自取/送货二选一；送货记录地址、驾车距离和费用，湛江全市可达，10km 内免费，超过 10km 的收费档位待定。不要用直线距离替代驾车距离。
- **质保：** 全新整机与本店全新配件 1 年，二手件 3 个月，客供件本身不在本店质保范围；本店配件部分按该配件保。延保支持独立费用与期限，定价仍待确认。
- **抵用：** 可拆分、无有效期；每次使用和剩余权益可追溯。找零的结算语义未定，先保留应付/未用额度，不能自作主张作废或变为一次性券。
- **预约：** 维修/服务记录上门或到店、时段、联系方式、地址及人员；先用清晰列表，排期视图可作为增强入口。
- **退单：** 保留原文定金与 10% 扣费的经营意图；实际退款页要记录原因、业务阶段、核实依据和最终处理额，不预设任何情况都自动扣费。

## 7. 资金和库存不可省略的约束

- 金额以整数分处理，由服务端重算；预算只辅助沟通。旧打印编辑器的元值只能通过明确适配转换。
- 库存区分可用、预留、待处理、在途与客户保管；库存数量和库存估值不能混用。
- 一件实物只允许一个有效预留；支付不直接正式扣库，正常销售在交付时扣库。
- 按数量管理和逐件管理分别核验；采购可分批到货、拒收、退货，不能按采购单创建数直接增加可用库存。
- 人工登记必须标识“线下收款”，保存方式、时间、经办人和核实依据；不伪装成平台支付回执。
- 首版就包括取消、预留释放、部分/全额退款与退回验机；退货验收后才决定回到可用还是待处理库存。
- 收款、退款、预留、到货、扣库均具备幂等、并发检查和操作记录；超时先查结果，不重建动作盲目重试。
- 已确认的报价有效期 24 小时和定金比例 15% 沿用为门店参数/条款快照；不把未经核实的“不退”表述做成无条件自动规则。

## 8. 延后事项与实施前问题

小程序在线支付、订阅消息、商城社区、营销积分、多门店调拨、自动抓价和复杂利润报表不阻塞 ERP 内部实现。回收拆件成本分摊、抵用流水、维修是完整首版必做，不属于延后项。
首版保留配置模板与人工报价，不扩大第三方电商接入。
现有演示照片只作为示意；验机、交付凭据必须用实际设备资料。

待对应任务前确认：预留到期天数、到期前提醒量、续期时长、置换剩余额度的结算方式、配送费规则。
先在原型中显示“待设置”或可配置字段，不编造默认业务承诺。未知成本显示“待核实”，不能当作零成本利润。
