# 03 · 业务规则、状态与核算

日期：2026-09-17。状态：拟实施规则；方案默认项见[范围决策](./01-scope-and-architecture.md)。入口：[总览](./README.md)。

本文件是本方案业务规则的唯一详细来源。两端不能各写一份库存 / 金额 / 状态判定。后端决定能否执行动作，前端解释结果。

## 1. 全域不变量

| 编号 | 不变量 |
|---|---|
| R01 | 金额以人民币整数分保存、传输和运算；未知成本为 null，不是 0；数量为正整数 |
| R02 | 型号、库存实物、客户设备、装机配置分别建模，不能用一个 SN 状态字段代替全部事实 |
| R03 | 库存必须区分门店所有与客户所有；客户暂存、客供、送修均不属于可卖库存 |
| R04 | 报价不锁货；成交预留；交付才销售出库；领料 / 装机只改占用或位置 |
| R05 | 同一逐件实物同一时刻最多一个有效预留；数量件占用总数不得超过可用量 |
| R06 | 已完成的资金、库存和折抵记录不直接改写或删除，使用关联冲销 / 退回 / 调整记录 |
| R07 | 每个关键动作带唯一 requestId 与版本前提；重复请求只形成一次有效结果 |
| R08 | 正式单据、成本、SN、质保、客户承诺保留快照；商品现价不能改历史 |
| R09 | 交易、履约、资金、检测、所有权、位置分别记录，不能互相猜测 |
| R10 | 两端成功反馈以服务端确定结果为准；断网草稿、原型示例、平台未对账必须明确标识 |
| R11 | 所有接口按当前成员和门店鉴权；客户输出使用独立白名单，不靠隐藏字段 |
| R12 | 一条业务动作内的库存、金额、实物关系、事件要么全部成功，要么全部不生效 |

时间：事件存 UTC 时间；界面和今日统计使用门店 Asia/Shanghai 日历日 00:00–24:00。日期范围传带时区的起止时间。服务器时间决定版本与事件顺序；预约时间、实际业务时间、创建记录时间分开。不能复制其他项目的凌晨换日规则。

## 2. 待办与统计

待办是从业务单据派生的读视图，不另维护一份可随意修改的任务状态。一个销售单 / 工单 / 回收单默认只有一条当前主待办，主键为 entityType + entityId；卡点优先于后续动作。例如缺 SSD 的单归“缺货”，不同时作为“可交付”重复出现。

排序：逾期 → 今天到期 → 当前可执行且等待最久 → 未来事项；同组按到期时间、创建时间、ID 稳定排序。未知交期排在同组已知交期之后，显示“待安排”。维修待客户确认仍可在列表查到，但按钮为“查看方案 / 记录确认”，不伪装为可开工。

| 指标 | 首版口径 | 点击结果 |
|---|---|---|
| 待交机 | 未取消且未交付、实物齐备、到交付阶段的销售单数 | 对应销售待办 |
| 缺货订单 | 未取消且未交付、至少一行未满足实际预留数量的销售单数 | 缺件与到货入口 |
| 维修待办 | 未归还、未关闭的维修工单数；包括待客户 / 返厂中的跟进事项 | 维修列表，可再按责任方筛选 |
| 待收款 | 已确认销售及已确认维修收费的正余额合计，不含草稿、初估、回收应付 | 应收明细，可包括已交付赊账单 |
| 待办总数 | 当前作用范围内的不同主待办条数 | 全部事项 |

统计默认覆盖本店未结事项；“今天”是工作入口，不意味着所有数值只统计今天新建。网页 / 小程序都显示作用范围，今日预约和逾期另用标签。分类数字不要求相加等于待办总数，待收款可以与缺货交付重合。一个已交付但欠款的订单继续成为“待收款”事项。

列表内搜索只搜当前事项；顶部全局搜索可查历史订单、客户、设备、SN。精确单号 / SN 优先，手机号搜索只在有权限时返回；结果和指标用同一个过滤快照，分页不改变汇总。

## 3. 销售与报价状态

### 报价

draft → issued → converted；issued 可过期或关闭。发出后修改形成新版本，不覆盖原客户版本。confirmedQuoteVersion 写入销售单。多份草稿可引用同一二手件；已失效的引用显示“需替换”，不静默变为同型号其他件。

草稿中的临时实物行可未建档；成交前必须映射到商品。客供 / 服务不要求店有商品库存，但来源类型必须明确。每个序列化 / 二手实物行数量为 1；多个同型号实物可分行或由独立分配记录逐件映射。

### 销售

交易状态：draft / confirmed / cancelled / closed。履约状态：waiting_stock / preparing / testing / ready_delivery / delivered。支付状态从流水计算，不设可编辑下拉框。

| 动作 | 前提 | 原子结果 | 失败后 |
|---|---|---|---|
| 保存草稿 | 输入可部分缺失，金额格式有效 | 保存草稿版本；不改库存资金 | 保留输入 |
| 确认成交 | 商品行映射、最终价格 / 质保、客户承诺完整 | 固化销售版本，预留可用新品，生成缺口；指定二手件如冲突则整次失败 | 返回冲突行，重新选择；不能擅自取消该行 |
| 补分配缺件 | 到货且合格，订单仍未交付 | 增加订单有效预留、减少缺口 | 不消费已被别人占用的货 |
| 开始装机 | 所需店有件已预留，客供件已接收 | 移至装机位置；数量保持，进入 preparing | 缺料保持 waiting_stock |
| 提交检测 | 对应配置版本、检测项目结果完整 | 记录检测事件；检测通过进入 ready_delivery，附件打包等交付收尾项仍可待办 | 不通过隔离故障件、释放该件预留并重新形成缺口 |
| 办理交付 | 见下文交付闸门 | 唯一销售出库、成本 / 配置 / 质保快照、交付凭据、客户设备关系、事件 | 全部回滚，不半交付 |
| 取消未交付单 | 原单未交付，说明原因 | 释放预留、取消履约；存在预收生成应退余额，单据保留 | 库存不重复增加 |

零售直接走 ready_delivery，不要求装机 / 烤机；按商品配置要求记录 SN 与质保，仍走共同交付动作。服务行无库存出库。首版订单整体交付，部分退货允许按行与数量处理。

### 检查单与交付闸门

检查模板可配置，但使用时固化模板版本。默认装机检查：配置与 SN 核对、点亮 / 测试结果、外观 / 附件打包。每项有执行人、执行时间、结果和必要说明。checkbox 是已完成事实的记录，不能代替真正测试。

ready_delivery 表示已到交付处理阶段，不表示已经满足所有交付闸门。因此陈先生可以列为“待交机”，同时仍有附件打包 1 项未完成；真正 deliver 时必须全部满足。

改配置 / 换件后，让受影响的配置核对与检测项失效；改附件则让打包项失效。交付前后端验证 checklist.configurationVersion 等于当前版本。

必须同时满足：订单有效、所有实物来源解决、有效预留未失效、需 SN 的行已准确绑定、检查通过、客户条款固化、款项结清或老板明确批准欠款交付、同一订单未交付过。允许进入“办理交付”核对页查看阻断原因，但“确认实物交出”必须等闸门通过。

尾款登记与交付首版采用两个清晰动作：先确认资金记录成功，再确认实物交付。资金成功而交付失败时保留已收记录，重试交付不能再收一次。客户端不得用两个隐藏请求伪装成永远成功的一个按钮。

欠款交付仅老板可执行，记录剩余金额、到期日、原因；支付状态仍未结清。不能让所有店员勾一个“跳过收款”绕过。

## 4. 库存与采购

自有在库量 = 可卖 + 已订 + 待处理，三类互斥。在途不算在库。客户保管另列。外送自有维修件仍属于自有资产，位置为外部、可用性待处理。

型号是否逐件管理是商品属性。二手一律逐件；新品按商品决定是否逐件 / SN。没有厂商 SN 的二手也有内部唯一 stockItemId / assetCode。SN 保留原始显示值并规范化检索；重复 SN 进入人工核对，不自动合并所有权记录。

| 事件 | 数量变化 | 所有权 / 说明 |
|---|---|---|
| 快速采购 / 采购实到验收 | 实到数量进入可卖或待处理 | 有采购 / 入库来源和成本，不能只录 SN 当完整采购 |
| 待检通过 | 待处理减少，可卖增加 | 不再新增一次总库存 |
| 成交预留 | 可卖减少，已订增加 | 仍为门店所有 |
| 领料装机 | 数量不变 | 保持预留，只改位置 |
| 交付销售 | 已订与在库同时减少 | 建交付 / 成本与客户拥有关系 |
| 未交付取消 | 已订减少，可卖增加；如损坏则入待处理 | 不增加在库总量 |
| 销售退回接收 | 在库与待处理增加 | 验收实物后；退款本身不触发入库 |
| 售后耗用自有备件 | 按领用动作减少备件在库，记录维修成本 | 独立于销售交付，不能免费就省略成本 |
| 报损 / 退供 | 对应自有在库减少 | 原因、责任和来源事件，老板权限 |

待检的预留件若故障，原子执行：撤销该件占用 → 待处理 → 原订单产生缺件。不能既在已订又在待处理导致数量重复减。

采购单数量 = 已合格入库 + 已拒收 / 取消数量 + 尚待到货数量（退供另有关联退供单）。部分到货按实到记录，多次验收各有 requestId；超量到货先修改确认采购量或建立追加采购，不静默增加。实到 SN 重复整笔返回逐行问题，不部分成功又报整体失败。

现买现入是同一动作生成简化采购与入库关系，可同时登记应付；付款独立登记。不要求先在供应商模块建档，但供应商称呼或散采说明必须有。

到货后不自动把货给任意最旧订单。显示缺口候选并选定分配对象；提交时按最新库存验证，特别避免到货被零售先卖掉后仍按旧数量装机。

盘点保存实盘结果不直接改库存。形成差异单，老板确认后生成调整事件；盘点时存在并发出入库必须以截止时点 / 事件序号对齐，不能拿昨天账面减今天实盘。

## 5. 回收与二手循环

回收主状态：draft → received_for_inspection → inspecting → offered → acquired → refurbishing → ready_for_sale；谈不成：return_pending → returned。所有权在 acquired 且接收确认完成时才转为门店，不能由“已付款”推断。

允许 acquired 后未付款，有应付；acquired 之后是否可卖由检测、整备、资料决定，付款状态不代替检测。若先付预付款但未取得所有权，仍不允许销售该物。

收购动作必须具备：卖方、明确实物、最终价、验机结论 / 已知缺陷、双方确认记录、实际接收事实。初估可变，最终收购以后变价走调整；不覆盖原价。客户放弃出售则归还附件和实物，不产生采购成本与可卖库存。

上架前必须补齐：逐件编号、成色、检测结果、必要整备、可归属成本、已知缺陷披露、销售价格、本店质保约定；存储设备有客户数据处置确认。普通备注不存客户密码。

成本例：U-017 收购 800 元＋已确认整备材料 80 元＝880 元。后续报价售价独立；成交预留 U-017，交付只确认 880 元成本，不新增“采购 880”现金。报价展示二手属性、成色、缺陷和本次质保；原卖方和收购成本只在内部权限内。

维修退回、销售退回沿用 stockItemId 和事件链，所有权按对应接收 / 转让事件确定。客户售后送回的同一件不自动变回门店资产；更换下来的旧件也不默认变为店有二手库存，必须明确归客户、返厂、报废或合法收购的去向。

整机拆件 / 预装库存首版默认关闭。若开启，另建 conversion 单：输入对象退出可售，输出对象形成、总成本守恒、残值 / 损耗单列；禁止手工同时增加整机和其零件。

## 6. 维修

received → diagnosing → awaiting_approval → repairing 或 outsourced → retesting → ready_return → returned → closed。可选“无需维修 / 客户拒绝”进入 ready_return，费用根据已确认检测约定处理；不能取消后让设备凭空消失。

接修无原销售单也可成立。记录客户描述、外观、附件、照片、联系办法、设备来源；内部诊断与客户描述分开。日期只能提供保修线索，最终处理依据需人工确认。

维修费用须有版本和客户确认记录，再领用收费配件。免费保内也要记录承担方；未确认价格不能记为确定应收。外包 / 返厂记录持有人、出发 / 返回、物流、费用、时间；寄出不等于已归还客户。

换件事件同时关联旧件、新件、工单、客户设备配置版本、备件成本、收费 / 免费原因与旧件去向。原销售快照不改，新增当前配置版本。旧件待检测不等于已收购。

归还前检查复测结果、附件、费用结清或有效欠款批准，记录实际归还人和时间；不强制收集身份证或电子签名。客户取机凭据与完整内部诊断分开输出。

## 7. 金额、折抵和退款

### 基础公式

金额字段以下均为整数分。每项是有效流水的净和；取消或冲销必须有引用，不物理删除。

冲销计算固定采用“原笔保留在净和中＋新增等额反向有效记录”，原笔带被冲销引用供显示和防重复。不能一边从净和剔除原笔、一边又计入反向记录而减两次。真实退款与纠正误录使用不同动作类型；界面分别标记。

- 销售净应计金额 = 原确认成交额 + 已批准加价调整 − 已批准减价 / 退货贷项。
- 现金净已收 = 有效实际收款 − 有效实际退款。
- 折抵净额 = 已生效折抵 − 已撤销折抵。
- 销售余额 = 销售净应计金额 − 现金净已收 − 折抵净额。
- 销售余额 > 0 为客户待付；= 0 为结清；< 0 为门店待退，不能直接显示为负尾款。
- 回收剩余应付 = 最终收购价 + 合法价款调整 − 有效折抵 − 现金净已付。

收款、应收、折抵、实收、交付销售额分别显示。登记微信收款只表示人工记录；可另标“待对账 / 已核对”，不声称支付 API 确认到账。

### 置换

| 场景 | 新机价 | 旧机最终收购 | 先前定金 | 折抵 | 本次现金 |
|---|---:|---:|---:|---:|---:|
| 正常 | 6,000 | 1,500 | 0 | 1,500 | 收 4,500 |
| 已付定金 | 6,000 | 1,500 | 500 | 1,500 | 再收 4,000 |
| 旧机更贵 | 6,000 | 7,000 | 0 | 6,000 | 付客户 1,000，记在回收应付 |
| 定金后旧机更贵 | 6,000 | 7,000 | 500 | 5,500 | 付客户 1,500，或经明确退款定金后折抵 6,000；首版固定前一种 |
| 未验机 | 6,000 | 预计 1,500 | 500 | 0，尚未生效 | 只显示预计补差，不允许结清 |

首版折抵金额 = min(销售当前正余额, 回收当前正应付)。一次折抵同时冲减双方义务，并关联同一 tradeInId；不可生成虚构现金收 / 付。双方当前交易主体须相同；不同主体代付首版不支持。

同一回收应付可部分折抵但累计不得超额；首版界面一笔置换对应一个销售单和一个可含多件实物的回收单。不能复制回收单复用同一实物。

撤销折抵不自动归还实物；退新机与退旧机收购分别处理。如果旧件已再售，不允许“恢复原状”制造不存在的库存或自动向原客户退款，需老板确认可执行的结算方案。

### 优惠与退款分摊

整单优惠仅分配给有价销售 / 服务行，客供件默认售价和成本为 0，另列装机服务费。按各行折前金额占比分配到分，先向下取整，余分按最大余数、再按稳定行 ID 分配。固化分摊结果；不得退款时重新按现价计算。

部分数量退货按原行净金额分配到每件；最后一件承担余分，累计退货贷项不超过原行净额。退货实物可待检，现金退款可稍后；二者独立。现金退款不得超过该单可退的净现金余额；需要把折抵权益退给客户时先明确关联结算处理，不凭空当原收款退。

可收款上限为当前销售正余额；可现金退款上限为负销售余额与该单可退现金净额中的较小值。例：成交 1,000、已收 1,000、确认退货贷项 300，余额 -300，退款 300 后余额回 0；库存先进入待检，绝不自动可卖。

### 成本与毛利

逐件按来源实际成本加确认整备；数量件维护总数量和总成本分：入库累加，出库按出库前平均成本分摊，四舍五入到分，最后一件带走剩余成本，保持总额守恒。存在未知成本的批次用待核实标志，不能估成零。

已交付实际毛利 = 净销售收入 − 对应已确认出库成本 − 按规则归属的直接成本。退款 / 退货通过关联调整反映，历史快照仍可查。毛利不等于净利润；销售未交付时只显示预计毛利。免费维修备件计维修成本，不再计一次原销售出库。

## 8. 权限默认表

| 动作 | 老板 | 普通店员 | 说明 |
|---|---|---|---|
| 待办、开单、查库存、检测、拍照 | 是 | 是 | 仅本店，按业务需要取资料 |
| 查看采购成本 / 毛利 / 完整账本 | 是 | 否 | 无权 API 不返回字段 |
| 登记收款、入库、交付 | 是 | 单独授权 | 一线可用但不可默认授予全部财务权限 |
| 确认回收最终价、确认折抵 | 是 | 否 | 店员可保存初估与验机 |
| 欠款交付、退款冲销、报损盘差 | 是 | 否 | 说明原因和金额 / 数量后确认 |
| 成员、权限、导出、绑定码 | 是 | 否 | 撤权后两个端的旧会话都须失效 |

沿用现有权限模型做映射，不直接相信客户端角色名。服务端通过 action + permission + entityState 三重校验。细分权限代码在 T01 冻结，与旧 quote/view、quote/edit 等明确映射，不让旧宽权限自动获得退款能力。

## 9. 超时、并发与回退

提交后状态可能是成功、确定失败或结果未知。结果未知不等于失败；保存 requestId 后查操作结果，必要时以相同 ID、相同载荷重发。载荷变更必须重新审核并使用新 ID。

电脑和小程序同时提交：实体 version 不一致时返回冲突；UI 保留草稿，展示最新事实。扣库 / 折抵约束必须在数据库写边界生效，不能只在写入前 SELECT 检查。具体实现见[接口契约](./04-data-and-api.md)。

错误修正优先追加补偿记录；代码回滚不等于数据库、现金和实物回滚。任何回退都须核对切换后的新增单据和操作，不能用旧备份覆盖新生意。
