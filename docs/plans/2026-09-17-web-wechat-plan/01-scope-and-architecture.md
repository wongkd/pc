# 01 · 产品边界与双端架构

日期：2026-09-17。状态：拟实施规格。入口：[方案总览](./README.md)。

## 1. 用户与目标

服务一家小型电脑装机店。电脑端与小程序都是老板 / 店员内部经营工具；微信登录不意味着普通微信用户可以查看门店业务。客户只接收明确生成的报价、交付或维修凭据；客户自助查单、商城不属于首版。

主线：接单 / 报价 → 成交 → 备货 → 装机检测或零售 → 收款交付 → 售后。回收、置换形成可用二手库存，并回到新的装机订单。

效果图固定的是风格和处理结构。日期、客户、金额、商品图片、状态均为示例；生产页面从服务端读取，不在组件中写死。

## 2. 决策与暂定规则

| 编号 | 内容 | 状态 / 影响 |
|---|---|---|
| D01 | 电脑网页＋微信小程序，不建设手机网页 | 用户明确；只为电脑网页验收桌面和平板窗口 |
| D02 | A+B 融合视觉和待办处理结构 | 按本轮指示作为实施视觉基准；不重开风格探索 |
| D03 | 单店，老板为主，少量店员 | 延续原规划；后端仍检查 storeId 与权限 |
| D04 | 微信采用原生 WXML / WXSS / TypeScript | 本方案技术选择；不新增跨端 UI 框架 |
| D05 | 首版不允许负库存、不允许静默赊账 | 安全默认；欠款交付须老板明确登记期限和原因 |
| D06 | 首版每张销售单整体交付 | 降低实现复杂度；确需分批交货，成交前拆成关联子单；已收款订单要先做受控金额分配，不能复制单据或重复款项 |
| D07 | 数量件按移动加权平均；序列化 / 二手按实物成本 | 方案默认；T05 用实际采购样本复核；历史缺成本保留未知 |
| D08 | 常见整机拆件、预装整机转库存 | 暂缓；禁止整机与部件同时可卖。若门店高频使用，增加转换任务并提升为上线必需项 |
| D09 | 收款方式为人工登记现金 / 微信 / 支付宝 / 银行 | 不接支付 SDK，不自动发消息 |
| D10 | 小程序用于内部人员，客户输出按白名单生成 | 不收集无关个人资料；不要求微信手机号授权才能使用 |

未知信息不阻塞文档和本地假数据开发；会影响真实数据、安全或发布的未知项必须在对应关口解决，不能让实现模型自行猜测。

## 3. 六模块的双端分工

| 模块 | 电脑网页 | 微信小程序 | 首版不做 |
|---|---|---|---|
| 今天 | 按交期 / 异常排序，选单即处理，照片看板 | 待办竖向列表、扫码找设备、详情处理 | 大图轮播首页、无动作的统计大屏 |
| 开单 | 模板、多行配置、替代方案、批量编辑、客户打印输出 | 新报价 / 零售 / 维修 / 回收入口，单行编辑，确认成交、登记款项 | 手机式多列配置表、自动硬件兼容承诺 |
| 库存 | 型号汇总、实物明细、采购、批量到货、盘点、导入 | 搜索、扫码、逐件到货、拍照、占用来源查询、少量盘点 | 小程序 Excel 导入和大批量编辑 |
| 售后 | 排期、方案和费用、换件、返厂、记录输出 | 接修拍照、检测、方案确认记录、归还 | 自动判定保修责任、远程控制客户电脑 |
| 回收置换 | 初估 / 验机 / 最终价、整备成本、关联折抵 | 接收旧物、拍照、逐项验机、老板确认收购和补差 | AI 自动估价、未验机直接可售 |
| 账本 | 明细、应收应付、日结核对、毛利、导出 | 今日收支 / 待收待付 / 单据查询；有权限者登记或冲销 | 完整会计总账、税务申报、把毛利称净利润 |

电脑六项顶栏：今天、开单、库存、售后、回收置换、账本；设置置于头像菜单。微信原生 tabBar：今天、开单、库存、更多。更多包括售后、回收置换、账本、客户查询、设置、账号。高频接修 / 回收在今天和开单各有快捷入口，无需总去更多。

“开单”作为导航进入报价与销售工作区；“＋开单”是新建动作，先选装机报价、配件零售、维修接收、回收 / 置换，避免名称相同却行为不明。

## 4. 范围分批与完成口径

| 阶段 | 内容 | 通过标准 |
|---|---|---|
| G0 基线 | 仓库、平台条件、契约、虚构样本、两端壳 | 文件可追踪，电脑与小程序入口明确，未连接生产 |
| G1 基础生意 | 商品、库存、采购、报价、成交占用、收款、装机交付、退货 | 缺货装机与零售闭环，两端处理同一单 |
| G2 必需循环 | 接修、换件、回收、整备、置换、二手再次装机、基本账本 | 五条业务路径与资金 / 库存可对账 |
| G3 试营业 | 权限、安全、输出、迁移、真机、性能、备份恢复 | 测试门店端到端通过，老板实务验收，生产切换另行授权 |

G1 可以演示，不能称完整首版。二手回收置换及再次装机是已确认需求，不因实施模型能力有限而挪到“以后再说”。不估计固定工期，按每张任务卡的证据判断进度。

## 6. 拟定工程结构

| 目录 | 职责与边界 |
|---|---|
| frontend/src/app/ | 网页路由、导航、布局、登录边界 |
| frontend/src/features/{workbench,sales,inventory,service,recovery,finance}/ | 各域页面、视图模型、服务；逐域建立，不一次搬空旧目录 |
| frontend/src/components/ui/ 与 styles/ | 网页基础组件和设计变量，不带金额、库存业务判定 |
| miniprogram/ | 新建的独立微信项目；project.config.json、miniprogram/ 应用源码、README；以实际模板确定配置路径并记录 |
| miniprogram/miniprogram/pages/ | 今天、开单、库存、更多、登录等主包入口 |
| miniprogram/miniprogram/packages/{sales,inventory,service,recovery,finance}/ | 按域组织详情、编辑、处理页；是否启用分包以实测包体和页面依赖为准 |
| miniprogram/miniprogram/components/ | 原生任务行、设备摘要、步骤、检查项、金额操作条、反馈面板 |
| miniprogram/miniprogram/services/ | wx.request 适配、登录、错误归一化、上传、动作结果查询 |
| contracts/ | DTO、枚举、错误码、脱敏 JSON 样本、版本说明；只存跨端可用契约，不引用 DOM / React / wx |
| backend/src/{routes,domains,repositories}/ | 路由鉴权、业务动作、D1 操作；边做边拆，index 保留分发 |
| backend/migrations/ 与 backend/tests/ | 只新增迁移；本地数据库约束、并发、幂等与故障测试 |
| docs/verification/<日期>-<任务>/ | 实际命令、截图、结果、未验证项和回退记录 |

当前 miniprogram 与 contracts 是拟建目录，本轮未创建。共享指的是协议和纯规则，不承诺 React 组件能放进微信，也不在首版引入复杂 monorepo 构建。若共享 TypeScript 无法被小程序直接编译，T01 选定单向生成到端内目录的流程并标识生成文件，禁止手工维护两份枚举。

## 7. 微信平台关口

| 项目 | 默认方案 | 什么时候必须落实 |
|---|---|---|
| AppID / 主体 / 开发成员 | 使用这家店的独立小程序；不得借用其他项目 | T00 登记是否具备，真机前填实际配置 |
| 登录 | 微信 code 由后端交换身份，再绑定已有门店账号 | T03；不让 openid 自动变老板 |
| 入店方式 | 首版采用电脑老板生成一次性绑定码，已登录且有权限；码短期有效且只能使用一次 | T03；不开放公众自行注册门店权限 |
| 域名 / 网络 | 独立 HTTPS API 与私有文件访问域名，配置微信相应域名项 | G0 做可达性预检，G3 开启域名校验真机测试 |
| 数据存储 | 继续评估 Workers / D1；照片用私有对象存储，具体服务在 T00 记录 | 不直接承诺现有海外端点适合店内与移动网络 |
| 平台规则 | 核查服务类目、隐私声明、备案及审核所需材料 | 发布准备时按实际主体和当时官方要求核实，不在方案中虚构资质 |
| 相机 / 相册 / 扫码 | 点击对应动作时调用，取消或拒绝仍可手输 | T16 真机；不把选图权限与经营身份绑定 |
| 消息 | 首版站内待办；订阅消息、公众号通知后置 | 未获用户授权不自动外发 |
| 支付 | 仅人工登记 | 若未来接支付，另立项目与验收口径 |

以上平台条件缺失时只阻塞相应联调或发布，不要求提前替用户注册服务、支付费用或改线上配置。
