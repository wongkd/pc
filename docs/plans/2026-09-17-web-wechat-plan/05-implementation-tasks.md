# 05 · 给低端模型的分步实施任务

日期：2026-09-17。状态：全部未开始；以下为后续执行卡，不是本轮编码授权。入口：[总览](./README.md)。

## 执行原则

每次只给模型一个任务编号；有 a / b / c 子卡时只给一个子卡。一个子卡只完成一个可验证结果，不让模型同时重构 App、写数据库、搭小程序并上线。界面、业务实现可以同属一个阶段，但分多次上下文执行。

每次最少阅读根 README、AGENTS、本目录 README、当前任务涉及的规格小节、上次交接与实际相关源码。无需整仓递归扫描 node_modules、备份、历史截图或所有旧规划。遇到规则冲突先引用文件与条款，不能自行“简化”库存或资金规则。

允许文件列的是候选范围。实际路径变化先更新任务卡与交接；不因为“重做”复制整个应用。业务切片的界面先接可复现 fixtures，切片完成时换成真实服务；生产模式禁止假数据降级。失败不能回退到 fixture 并显示成功。

每次结束只标本卡状态：未开始 / 进行中 / 待核实 / 本地通过 / 平台通过。没有运行的检查写“未运行”，截图只证明界面，测试结果只证明其覆盖范围。禁止把测试数量当业务完成度。

## 依赖与里程碑

T00 → T01 → T02；T03 与 T04 在各自前置完成后继续。真实业务写入依赖 T03（身份）与 T04（一致性）。

G1：T05 商品库存 → T06 采购入库 → T07 报价 → T08 成交占用 → T09 资金 → T10 交付 → T11 退货。

G2：T12 售后、T13 回收整备 → T14 置换再装机 → T15 账本；依赖 G1。照片、输出和页面整合分别由 T16 / T17 / T18 完成；它们必须在 G2 最终验收前接通。

G3：T19 兼容 / 安全 → T20 迁移演练 → T21 双端验收。正式发布属于 T22，必须有后续明确授权，不能从“本地通过”自动继续。

设计壳和契约在 G0 完成不意味着登录、真实存储或业务完成。

## 统一任务提示词

以下文字用于未来实施时复制，替换任务编号即可；不是对本轮的执行命令。

> 请执行 docs/plans/2026-09-17-web-wechat-plan/05-implementation-tasks.md 的【Txx 子卡】。先读根 README、AGENTS、方案 README 和该卡指定章节、上次交接，再核实实际源码与 Git 状态。本次只实现这一张子卡，不做手机 H5，不改视觉方向，不拓展模块，不发布、不操作生产数据。
>
> 以 03 的业务规则和 04 的接口契约为准。先列本次实际文件范围与验收样本，然后实现；普通可逆实现无需逐步索要确认。涉及尚未确定的业务 / 平台条件时记录具体缺项，继续不依赖它的部分，不猜测身份、金额、库存或授权。
>
> 完成后运行与改动相关的检查，记录精确命令与结果。失败保留输入 / 业务事实，不用假数据、前端状态或跳过检查伪装成功。不得删除现有测试以求通过。
>
> 最后交付：改了什么、实际验证、未验证范围、已知问题、下一子卡；更新该任务验证目录与交接。若卡内仍有未完成项，不标通过，也不自动启动下一卡。

## 每次交接模板

| 字段 | 填写内容 |
|---|---|
| 当前卡 / 状态 | 例如 T08b，本地通过 / 真机未验证 |
| 实际环境 | 路径、分支与提交 / 未提交范围、API / 数据库环境标识 |
| 读取依据 | 规格章节、契约版本、补充决定及来源 |
| 实际改动 | 文件与职责；说明与原有文件的兼容关系 |
| 数据变化 | 新迁移文件、仅本地执行还是未执行；不得笼统写“已迁移” |
| 验证证据 | 命令、时间、环境、结果、截图 / 报告路径 |
| 未完成 / 阻断 | 具体原因、影响、可继续的独立工作 |
| 下一步 | 下一个明确子卡，前置是否满足 |

只有完成相应关口后才汇总“阶段通过”。不同任务的结果只在自己的验证目录记录，根 README 只留入口，避免出现多份互相矛盾的业务规则。
