# 配件收发主线：ERP 流程复评与简化方案

- 日期：2026-09-26
- 状态：V2 网页已发布到生产；本轮改动限于导航、报价说明、回收详情和置换操作体验，不改数据模型或生产数据。员工真实业务闭环仍待验收。
- 目标：让报价、采购到货、回收置换、维修用料和销售履约都围绕“具体配件/实物最终怎样入库、怎样出库”组织。
- 入口：本文件。
- 范围：网页 ERP 员工操作流程。顾客小程序、资金规则和现有服务端安全边界不在本轮重定。

## 结论

目前系统把业务分成报价、销售、采购、库存、回收、置换、售后等独立页面，再要求员工理解它们之间的先后和关联。业务规则越来越完整，但员工仍要在多张单据间搬运同一个实物、客户和金额。最近发布的回收分步指引增加了说明，没有减少实际操作；详情页又把指引、附件、置换、实物表、其他操作和各动作表单纵向堆在一起，常见动作难以一眼找到。V2 按实物去向聚合入口并减少首屏并列内容，同时保留每种来源自己的账本。

新的主线应是：**每次实物边界变动只产生一条真实入库或出库流水；业务单据是动作的来源和上下文，重复提交不能重复记账。** 员工先选要处理的配件，再选“收进来”或“交出去”；系统负责把来源单、成本、客户、订单和资金记录关联起来。

报价是成交预期，不产生入库或出库。预留只表示暂时不能卖给别人，不等于实物已经出库。货物实际交付、维修实际领用或其他真实离店动作才记出库。回收取得所有权、采购实收、客户退货和拆件产出才记入库。

## 现状证据与体验问题

1. 主导航将“库存”和“回收置换”分开；销售工作区又把报价、订单和交付分开。配件流转实际需要在多个业务词汇间来回转换。
2. 生产回收详情页实看包含四步指引、金额摘要、附件、单独的置换关联区、实物表、可执行操作和展开后的操作表单。置换仍要求选一张同客户销售单、建立关联、再填写金额；散客无法抵扣时，页面让员工改走付款登记。规则有必要，但呈现和关联成本过高。
3. 报价行允许自定义商品，也逐行录入名称、规格、来源、数量、单价和备注；部分来源还要求再关联实物。草拟报价本来不应动库存，但员工容易把“报价商品”和“实际库存实物”混为一件事。
4. 生产库存入口当前显示暂无商品档案，且期初录入没有启用。当前页面无法自然地从“我手里有这批货”开始建库存。真实库存尚未录入也记录在 [STATUS](../../STATUS.md)。
5. 当前追踪能力仍分裂：批次记了入库数量但没有批次出库余量，旧 SN 台账又独立于新实物台账。只把前端页面合并会掩盖这条账本缺口。

## 建议的员工心智模型

员工主导航收敛为五个：

1. **今天**：只列下一步待办，如待验机、待收货、待备料、待交付、待付款；每项只有一个主动作和具体卡点。
2. **开单**：报价、成交、收款和交付围绕同一个销售单；报价可以使用商品、实物、服务或临时报价行。
3. **实物流转**：按型号汇总，也能直接查到逐件实物或批次；采购到货、收旧件、库存和 SN 深链归到同一入口组。具体入/出库仍由采购、回收、销售或维修来源单发起。
4. **售后**：保留检测、维修、客户确认等服务工作；配件更换由维修单触发配件出库，不能另录一笔重复库存调整。
5. **账本**：只记实际收付及已发生的折抵。报价、估价和未付款承诺不能当现金流水。

回收不再要求员工先理解一套独立的“回收系统”，再跳到“置换系统”。从“收旧件”进入：登记实物和卖方 → 验机/确认收购 → 选择整机再售或拆件。若同时成交，从当前回收单选择同一客户销售单并填写折抵金额，一次启动关联和折抵；这是两个既有服务端写操作，不是数据库原子事务。若折抵失败，已建关联会保留，员工可从该单续办，不能重复建关联。若没有对应销售单，则形成待结算应付；只有现实里确实付款后才登记付款。

## 收发动作设计

### 入库：从手上实物开始

同一个收货入口支持单件和批次两种记录方式，默认只问完成入库必需的信息：

- 来源：采购、回收/置换、客户退回、维修返还、期初或拆件产出。
- 配件/型号、数量及成色；单件自动生成内部编号，厂家 SN 可选，耗材按批次管理。
- 成本：已知成本、估算成本、未知或零成本按现有经营规则区分。
- 入库去向：可卖、待检/隔离、客户保管等按来源给出安全默认值。
- 备注和证据可选并折叠，不要在普通收货时要求员工先建多张单。

采购单仍用于未到货数量和供应商应付；实到多少就只对多少写入库。现买现入从收货页一次提交，后台保留所需的采购和库存来源关系。任何入库动作都要幂等，失败或结果未知时保留输入并能查询原操作。

### 出库：从即将离开门店的配件开始

- 销售：成交后先预留具体库存；交付完成时一次性出库。
- 零售现货：选择现有配件并确认已交付，可在同一流程完成收款登记或记录未收金额；不强迫先建整机订单。
- 维修：从维修单选已更换/领用的配件，确认后出库。
- 拆件：源整机作为拆解出库；产出的可用配件作为新入库。产出成本加损耗必须等于源件成本。
- 退供应商、退客户或报损按各自权限和冻结规则形成有原因的出库流水，不允许直接改库存数字。

预留是可售数量的占用态，不是出库。只有实物真的离开门店/所有权改变时才产生最终出库流水；撤销或取消只释放预留，不伪造反向库存动作。

### 报价和置换：作为收发动作的业务上下文

- 报价用搜索选择型号/实物，也允许暂时报价行；模板带出常用配置。库存提示只帮助判断，不改变在库数，也不自动采购。
- 从报价转成交单时复核实际出售的配件和数量，自动预留可用库存；缺货才进入待采购队列。
- 旧配件折抵应直接从该销售单的客户和余额出发。员工录入旧件一次，即同时得到回收入库来源与销售折抵关联；不再分别新建回收、搜索销售、建立关联、重新填写折抵额。
- 现金付款与折抵仍是两类记录。系统可以展示“待付”，但不能把估价自动做成付款，也不能代发转账。

## 页面规则

- 详情首屏只显示：当前状态、库存影响、金额影响、唯一推荐下一步。其他动作放在“更多操作”。
- 不在每张单重复常驻展示操作教程；用字段旁的短提示解释具体阻塞原因和解决动作。
- 当前动作表单只在选中后展开；附件、历史、成本明细收在下方或折叠区，减少长页滚动。
- 一个实物/批次详情显示来源单 → 入库 → 预留/保管 → 出库/去向的时间线；所有入口最终回到同一条目。
- 商品型号、逐件实物和批次是不同层次，界面可以同一入口，但必须明确员工正在录型号、单件还是一批数量。
- 常见操作支持扫码、键盘连续录入、默认值和上次选择；错误保留当前输入，不能要求回列表重新开始。

## V2 实施边界

V2 先利用现有 API 梳理信息层级和动作顺序，不建一个来源不明的通用收发单，不修改账本 schema、契约、迁移或生产数据。已做的网页调整包括：

- 主导航由六个业务词改为五个工作区，“库存 / 采购 / 收旧件”归到“实物流转”；配件台账首屏集中采购到货、收旧件和销售交付入口，常用快捷入口保留报价与客户。
- 配件台账和报价编辑器直接标明库存边界：报价不改库存、预留不等于出库，实际交付后才记出库。
- 回收详情首屏突出当前库存影响和推荐动作；金额明细、附件和完整规则收起，逐件实物放在结算区前面。
- 置换从选销售单、填金额到应用折抵只有一个主动作；调用前后端版本及金额校验不变，失败后留在原关联续办。

## 明确保留的后端缺口

- 同一 UI 动作不代表所有写入原子完成；置换仍是先建关联再应用折抵两个幂等操作，前端必须准确提示并能续办。
- 批次已记入库数量但未追踪出库余量；旧 SN 台账未并入新实物详情。
- 维修耗件与销售实物的批次/单件映射、一个旧件拆成多个产出的完整成本链，需另行核实服务端和契约支撑。
- 本轮不宣称解决上面几项；不以导航聚合或 UI 文字替代数据库流水。

任何 schema、契约、generated、入口接线改动须作为单独任务，从最小缺口开卡并遵循共享单点流程；本次 V2 网页发布不包含此类改动。

## 验收场景与目标

- 新建报价：模板/搜索录入配置，保存和发出不改变库存。
- 成交且有库存：一次确认后可查到预留；交付后每个真实配件只出库一次。
- 缺货：报价仍可发出；成交后只为缺件采购，到货数量一次入库，后续交付一次出库。
- 回收置换：同一界面录旧件和当前销售单折抵，能查到一条入库和一条非现金折抵；取消/重试不重复记账。
- 单独回收：收购后只入待检；付款状态待处理，实际付款后登记现金流水。
- 拆件：源机出库，零件按数量入库，成本平衡可见。
- 维修换件：领用件出库，维修单能追到实物；取消不能留下重复流水。
- 耗材批次：入库、部分领用、剩余量一致，不能只记入库不跟踪出库。
- 典型收货/出库不需要跨多个主导航页面；首次使用者能仅凭一个主动作完成，不必读完整教程。

建议目标：普通单件收货或单件零售控制在一个页面、一个提交动作、四项以内必填；报价新建只先要求客户（可散客）和明细，不要求员工跳出报价页建库存。以上是待原型验证的目标，不是已经测得的耗时。

## 明确不做

- 不把报价、估价、预留当成库存入库/出库。
- 不让前端自行改库存数，不绕过付款、折抵、成本、所有权、权限或版本校验。
- 不用“通用收发单”掩盖采购到货、回收取得、销售交付的业务来源。
- 不在原型评审前改 `contracts/v1`、generated、`backend/src/index.ts` 接线或迁移。
- 不把现有员工生产交易用作试填样本；原型用合成数据，生产迁移和库存初始化另行核对。
