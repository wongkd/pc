## 1. 一句话结论

顾客**看配置单 → 可能反复改 → 确认 → 自己下单付款**。
这是**循环**，不是直线；每一次改动都是**新版本**；钱到手才锁机器。

---

## 2. 状态流转

```
草稿（你编辑）
   ↓ 发出
已发给顾客（可看、可提意见）
   ↓ 顾客要改 ──→ 回到草稿，版本 +1   ← 这个循环可以走很多次
   ↓ 顾客确认
已确认（配置与价格锁定，不能再改）
   ↓ 顾客自助下单
已核实预付款（15%）→ 尝试锁定库存，再按缺件采购
   ↓
已付全款 → 装机 → 交付
```

**两个关键分界**：

| 分界 | 之前 | 之后 |
|---|---|---|
| **顾客确认** | 可以反复改，每次改生成新版本 | 配置与价格锁定，要改必须重新确认 |
| **达到已核实预付门槛** | 不锁库存、不触发采购 | 尝试预留，7天到期复核，已付款不机械自动释放 |

## 4. 系统实现要点

- **锁库存的硬保证**：`backend/migrations/0007_inventory_core.sql:245`
  `CREATE UNIQUE INDEX ... ON stock_reservations(stock_item_id) WHERE status = 'active'`
  —— 同一件库存同时只允许一条生效中的预留，靠数据库约束，不是代码判断。
  ⚠️ 这是**部分唯一索引，只有 PostgreSQL 支持，MySQL 不支持** ⇒ 后端迁 CloudBase 必须选 PostgreSQL。

- **顾客端只读**：顾客看到的配置单是只读的，改的动作全部回 ERP。因此小程序端不需要购物车、搜索、自助改配置。

- **六态不泄漏**：未登录 / 无权访问 / 失效 / 加载中 / 加载失败 / 已撤回 六种状态下，
  不得出现任何金额、配件名与「预算」字样（Q01 原型已定规则①，硬断言，不是前端隐藏）。

- **预算对照条**：预算**不进金额计算**，措辞不写"省"，超预算转警示色但不劝退不催付（Q01 原型已定规则⑤）。

## 6. 已知风险（不阻塞，但要知道）

- **专门订货的15%预付款可能盖不住损失**。首版由老板评估是否接单；不能临时追加未确认的不退条款，也不把采购支出全部当可扣损失。
- **24 小时有效期偏短**：装机是几千上万的消费，顾客决策周期通常不止一天。
  栋哥选择保留紧迫感，配"到期提醒 + 手动续期"来兜底。若后续发现反复续期太累，可放宽到 3–7 天。
